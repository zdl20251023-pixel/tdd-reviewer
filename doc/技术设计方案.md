# TDD-Reviewer 技术设计方案

> **版本**: v1.0  
> **日期**: 2026-05-16  
> **目标文件**: `index.ts`

---

## 1. 系统定位与业务目标

TDD-Reviewer 是一个**基于 AI 的技术设计文档（TDD）自动化审查工具**。它接收一份 Markdown 格式的技术设计文档作为输入，通过多阶段 AI 管线进行结构化提取、交叉漏洞分析、混沌注入测试，最终输出一份包含方案评估、P0 漏洞清单、优化建议、深度解析和混沌测试结果的审查报告。

**核心价值主张**：用 ECS（Entity-Component-System）架构思想组织 AI 审查流程，将"一次性大 Prompt 生成"拆解为"结构化提取 → 多维交叉分析 → 模板+AI 混合渲染"的三阶段管线，以提升审查的精度、深度和格式可控性。

| 层级 | 技术选型 | 用途 |
|:-----|:---------|:-----|

## 3. 架构设计：ECS 审查管线

### 3.1 设计思路

借鉴游戏引擎中的 ECS 架构模式，将 TDD 文档审查抽象为：

```
Entity（功能模块） + Component（属性维度） + System（审查逻辑）
```

整体流程：

```
input.md ──→ [Phase 1: Entity Extractor] ──→ Entity[]
                                                │
                            ┌───────────────────┼───────────────────┐
                            │                   │                   │
                            ▼                   ▼                   ▼
                    [System 1-3]         [System 4]          [System 5]
                    交叉漏洞分析         混沌注入测试        防腐层审计
                            │                   │                   │
                            ▼                   ▼                   ▼
                    Vulnerability[]      ChaosResult[]      Vulnerability[]
                            │                   │                   │
                            └───────────────────┼───────────────────┘
                                                │
                                    [Phase 3: 混合渲染管线]
                                    模板硬渲染 + AI 生成
                                                │
                                                ▼
                                           output.md
```

### 3.2 Entity 与 Component 定义

每个 Entity 代表 TDD 文档中的一个**功能模块**（如 `UserLoginFlow`、`AICoachPipeline`），携带三个 Component：

| Component | 关键字段 | 描述 |
|:----------|:---------|:-----|
| `state` | `storageType`, `consistencyLevel`, `mutationPoints` | 状态变更维度 |
| `ai` | `modelCalls`, `hasAntiCorruptionLayer`, `contextAssembly`, `nonDeterministicRisks` | AI/LLM 调用维度 |
| `concurrency` | `entryPoints`, `isolationMechanism`, `sharedResources` | 并发场景维度 |

每个 Entity 还携带 `sourceExcerpt` 字段，保留原文中与该模块直接相关的段落，确保后续 System 分析时有原始上下文可引用。

### 3.3 System（审查系统）查询机制

5 个 System 通过 Component 组合查询筛选目标实体，模拟 ECS 的 Query 机制：

| System | 查询条件 | 审查焦点 |
|:-------|:---------|:---------|
| StateConcurrency | `state.involved && concurrency.involved` | 竞态、脏数据、死锁 |
| AiState | `ai.involved && state.involved` | AI 非确定性输出污染持久化层 |
| AiConcurrency | `ai.involved && concurrency.involved` | 高并发下 AI 服务雪崩 |
| ChaosInjection | 所有实体 | 故障注入 + 降级兜底检测 |
| AntiCorruptionAudit | `ai.involved` | 防腐层完整性审计 |

## 4. 三阶段管线实现细节

### Phase 1：实体提取（Entity Extractor）

- **实现**：单次 `generateObject` 调用，使用 Zod Schema 约束输出结构
- **输入**：原始 TDD 文档全文
- **输出**：`Entity[]` 数组
- **关键设计**：Component 不是布尔开关，而是携带具体数据的结构体（如 `storageType: "Redis"`）

### Phase 2：并行交叉审查（Parallel Check Systems）

- **实现**：`Promise.all` 并行拉起 5 个 System，零数据依赖
- **每个 System**：独立的 `generateObject` 调用，带专属 System Prompt
- **输出**：`Vulnerability[]` + `ChaosResult[]`
- **后处理**：代码层硬过滤 P0 级漏洞，上限 5 条

### Phase 3：混合渲染管线（Few-Shot Enhanced）

采用**模板硬渲染 + AI 生成**的混合策略：

| 章节 | 渲染方式 | 说明 |
|:-----|:---------|:-----|
| §1 方案评估 | AI 生成（路线 A） | 与 §3 合并为一次 `generateText` 调用 |
| §2 潜在风险 | **模板硬渲染** | 100% 格式可控，直接遍历 `Vulnerability[]` |
| §3 优化建议 | AI 生成（路线 A） | 同上 |
| §4 深度解析 | AI 生成（路线 B） | 注入 Few-Shot 样本，教会 AI 锐利洞察风格 |
| §5 混沌测试 | **模板硬渲染** | 100% 格式可控，只展示最严重的 3 个 |

- **路线 A** 和 **路线 B** 通过 `Promise.all` 并行执行
- 路线 B 使用 `messages` 数组注入 Few-Shot 样本（来自 `doc/审查-分析结果.md`）
- 最终由 `assembleDocument()` 函数通过正则从 AI 输出中提取章节并按顺序拼接

## 6. 当前方案优点

### 6.1 架构层面

| 优点 | 说明 |
|:-----|:-----|
| **ECS 解耦思想** | 将"实体提取"与"漏洞分析"彻底解耦，每个 System 只关注特定的 Component 组合，职责单一 |
| **并行化执行** | Phase 2 的 5 个 System 和 Phase 3 的 2 路 AI 调用均通过 `Promise.all` 并行，最大化吞吐 |
| **Component 数据密度高** | 从布尔开关升级为携带 `storageType`/`mutationPoints` 等具体数据的结构体，显著提升后续分析精度 |
| **sourceExcerpt 上下文保留** | 每个 Entity 保留原文摘录，解决了"Phase 2 丢失原始文档"的问题 |

### 6.2 质量控制

| 优点 | 说明 |
|:-----|:-----|
| **Zod Schema 强约束** | 所有 AI 输出通过 `generateObject` + Zod Schema 校验，保证结构化输出的类型安全 |
| **P0 硬过滤** | 代码层 `.filter(v => v.level === "P0").slice(0, 5)` 硬性控制输出质量，不依赖 AI 自律 |
| **模板+AI 混合渲染** | §2 和 §5 用模板硬渲染确保格式 100% 可控，AI 仅负责需要创造性的章节 |

### 6.3 工程实践

| 优点 | 说明 |
|:-----|:-----|
| **Few-Shot 增强** | 通过注入高质量审查样本，引导 AI 输出风格（锐利、引用具体代码实体） |
| **降级容错** | Few-Shot 文件加载失败时自动降级为无样本模式（`.catch(() => "")`），不阻断管线 |
| **日志可观测** | 每个 Phase 和 System 都有 emoji 标记的 console.log，便于调试和性能分析 |

## 7. 当前方案不足

### 7.1 P0 级：架构缺陷

| 编号 | 问题 | 影响 |
|:-----|:-----|:-----|
| **P0-1** | **Phase 1 单点故障** | 实体提取是单次 AI 调用，一旦漏提关键模块，后续所有 System 永远看不到该模块，整条管线质量被 Phase 1 锁死 |
| **P0-2** | **assembleDocument 正则解析脆弱** | 依赖正则 `match(/### 1\. 方案评估[\s\S]*?(?=### [23]|$)/)` 从 AI 自由文本中提取章节，AI 输出格式稍有偏差即解析失败 |
| **P0-3** | **零重试 + 零错误恢复** | 7 次 AI 调用任一失败直接 `process.exit(1)`，无单点重试、无断点续跑机制 |

### 7.2 P1 级：质量与成本

| 编号 | 问题 | 影响 |
|:-----|:-----|:-----|
| **P1-1** | **漏洞去重缺失** | 5 个 System 独立运行，同一漏洞可能被多个 System 重复发现，输出冗余 |
| **P1-2** | **上下文截断硬编码** | `tddContent.slice(0, 3000)` / `slice(0, 4000)` 对长文档直接截断，可能丢失后半部分关键模块 |
| **P1-3** | **模型无差异化** | 所有 7 次 AI 调用统一使用 `gemini-3-flash-preview`，未根据任务复杂度区分模型 |
| **P1-4** | **Token 成本不可控** | 7 次 AI 调用 × 每次注入大量 JSON 上下文，总 Token 消耗无监控、无预算控制 |

### 7.3 P2 级：工程质量

| 编号 | 问题 | 影响 |
|:-----|:-----|:-----|
| **P2-1** | **单文件 550 行** | 所有逻辑（Schema、System、渲染、主流程）挤在一个文件中，可维护性差 |
| **P2-2** | **无类型导出** | 核心类型仅文件内部使用，无法被测试或其他模块引用 |
| **P2-3** | **无配置外化** | 输入输出路径、P0 上限（5）、混沌展示量（3）、截断长度等均硬编码 |
| **P2-4** | **无单元测试** | 纯函数 `renderVulnerabilitiesSection` / `assembleDocument` 无测试覆盖 |
| **P2-5** | **无运行脚本** | `package.json` 缺少 `"start": "tsx index.ts"` |

## 8. 改进方案

### 8.1 P0 级改进：核心可靠性

#### 8.1.1 Phase 1 双重提取 + 合并去重

```
原文 ──┬──→ LLM 提取 (全文前半段) ──→ Entity[] A
       └──→ LLM 提取 (全文后半段) ──→ Entity[] B
                                        │
                                   合并去重 (by id)
                                        │
                                   Entity[] Final
```

- 对长文档分段提取，再按 `entity.id` 合并去重
- 引入"实体完整性校验"：检查提取出的实体是否覆盖了文档中所有 `##` 级标题

#### 8.1.2 渲染管线改用结构化输出

将路线 A 从 `generateText` 改为 `generateObject`，彻底消除正则解析的脆弱性：

```typescript
// Before: 自由文本 + 正则提取（脆弱）
const { text } = await generateText({ ... });
const section1 = text.match(/### 1\. 方案评估[\s\S]*?(?=### [23]|$)/);

// After: 结构化输出（确定性）
const { object } = await generateObject({
  schema: z.object({
    section1_评估: z.object({
      架构逻辑: z.string(),
      技术选型: z.string(),
      状态流转: z.string(),
    }),
    section3_优化: z.object({
      防御性方案: z.array(z.string()),
      降本增效: z.array(z.string()),
    }),
  }),
  ...
});
```

#### 8.1.3 单点重试 + 断点续跑

```typescript
async function withRetry<T>(
  fn: () => Promise<T>,
  label: string,
  maxRetries = 2
): Promise<T> {
  for (let i = 0; i <= maxRetries; i++) {
    try { return await fn(); }
    catch (e) {
      if (i === maxRetries) throw e;
      console.warn(`⚠️ [${label}] 第 ${i+1} 次重试...`);
      await new Promise(r => setTimeout(r, 1000 * (i + 1)));
    }
  }
  throw new Error("unreachable");
}
```

### 8.2 P1 级改进：质量提升

#### 8.2.1 漏洞去重系统

在 Phase 2 后增加去重步骤，可选两种方案：

- **轻量方案**：基于 `title` 关键词匹配去重
- **高级方案**：增加一个专门的 AI 去重 System，让 LLM 合并语义重复的漏洞

#### 8.2.2 智能上下文管理

```typescript
function smartTruncate(text: string, maxTokens: number): string {
  const estimatedCharsPerToken = 1.5; // 中文约 1.5 字符/token
  const maxChars = Math.floor(maxTokens * estimatedCharsPerToken);
  if (text.length <= maxChars) return text;
  const head = text.slice(0, maxChars * 0.6);
  const tail = text.slice(-maxChars * 0.3);
  return `${head}\n\n... [中间内容已省略] ...\n\n${tail}`;
}
```

#### 8.2.3 模型分级策略

| Phase | 推荐模型 | 理由 |
|:------|:---------|:-----|
| Phase 1 实体提取 | Flash | 结构化提取任务，Schema 约束已足够 |
| Phase 2 System 1-5 | Flash | 焦点明确，Prompt 已高度专化 |
| Phase 3 路线 A | Flash | 有结构化数据驱动，不依赖创造性 |
| Phase 3 路线 B 深度解析 | **Pro** | 需要高质量的降维类比和深度洞察 |

## 9. 总结

TDD-Reviewer 的 ECS 管线架构在**设计理念**上是优秀的：通过实体-组件-系统的解耦实现了多维度交叉审查，并行化执行提升了效率，Zod Schema 保证了 AI 输出的结构化可靠性，模板+AI 混合渲染平衡了格式可控与内容深度。

当前最核心的三个改进方向：

1. **Phase 1 单点容错**（双重提取 + 合并）— 消除管线质量被锁死的风险
2. **渲染管线正则替换为结构化输出**（消除 `assembleDocument` 的脆弱性）
3. **工程化拆分**（单文件 → 多模块）— 提升可维护性和可测试性

这三项改进将使系统从"可用的原型"进化为"可靠的工具"。
