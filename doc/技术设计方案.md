# TDD-Reviewer 技术设计方案

> **版本**: v4.0 (Refactored)  
> **日期**: 2026-05-16  
> **代码入口**: `index.ts` → `src/pipeline.ts`

---

## 1. 系统定位与业务目标

TDD-Reviewer 是一个**基于 AI 的技术设计文档（TDD）自动化审查工具**。它接收一份 Markdown 格式的技术设计文档作为输入，通过多阶段 AI 管线进行结构化提取、交叉漏洞分析、混沌注入测试，最终输出一份包含方案评估、P0 漏洞清单、优化建议、深度解析和混沌测试结果的审查报告。

**核心价值主张**：用 ECS（Entity-Component-System）架构思想组织 AI 审查流程，将"一次性大 Prompt 生成"拆解为"结构化提取 → 多维交叉分析 → 模板+AI 混合渲染"的三阶段管线，以提升审查的精度、深度和格式可控性。

## 2. 技术栈

| 层级 | 技术选型 | 用途 |
|:-----|:---------|:-----|
| 运行时 | Bun / Node.js + TypeScript | 脚本执行 |
| AI SDK | Vercel AI SDK (`ai` v6) | `generateObject` / `generateText` 统一调用 |
| 模型 | Google Gemini (`@ai-sdk/google`) | 分级模型策略（Flash 提取分析 / Pro 深度解析） |

| 配置 | dotenv + `src/config.ts` | 环境变量 + 配置中心化 |

## 3. 架构设计：ECS 审查管线

### 3.1 设计思路

借鉴游戏引擎中的 ECS 架构模式，将 TDD 文档审查抽象为：

```
Entity（功能模块） + Component（属性维度） + System（审查逻辑）
```

### 3.2 模块化工程结构（v4 实现）

```

├── src/

│   ├── pipeline.ts             # 主管线编排器（三阶段流程控制）
│   ├── schemas/                # Zod Schema + 类型导出
│   │   ├── entity.ts           # Entity + 3 个 Component Schema
│   │   ├── vulnerability.ts    # 漏洞 Schema
│   │   ├── chaos.ts            # 混沌测试结果 Schema
│   │   └── index.ts            # Barrel Export

│   │   ├── entity-extractor.ts # Phase 1：双重提取 + 合并去重
```

### 3.3 整体流程

```
input.md ──→ [Phase 1: Enhanced Entity Extractor] ──→ Entity[]
              (双重提取 + 合并去重)                       │
                                      ┌──────────────────┼──────────────────┐
                                      │                  │                  │
                                      ▼                  ▼                  ▼
                              [System 1-3]        [System 4]         [System 5]
                              交叉漏洞分析        混沌注入测试       防腐层审计
                                      │                  │                  │
                                      ▼                  ▼                  ▼
                              Vulnerability[]     ChaosResult[]     Vulnerability[]
                                      │                  │                  │
                                      └──────┬───────────┼──────────────────┘
                                             │           │
                                        去重 + P0 过滤   │
                                             │           │
                                  ┌──────────┴──────┐    │
                                  ▼                 ▼    ▼
                           路线A: generateObject  路线B: generateText   模板硬渲染
                           (§1+§3 结构化输出)   (§4 Few-Shot 深度解析) (§2+§5)
                                  │                 │         │
                                  └────────┬────────┘─────────┘
                                           ▼
                                  assembleDocument()（零正则拼接）
                                           │
                                           ▼
                                      output.md
                                           │
                                      Token 用量汇总
```

### 3.4 Entity 与 Component 定义

每个 Entity 代表 TDD 文档中的一个**功能模块**，携带三个 Component：

| Component | 关键字段 | 描述 |
|:----------|:---------|:-----|
| `state` | `storageType`, `consistencyLevel`, `mutationPoints` | 状态变更维度 |
| `ai` | `modelCalls`, `hasAntiCorruptionLayer`, `contextAssembly`, `nonDeterministicRisks` | AI/LLM 调用维度 |
| `concurrency` | `entryPoints`, `isolationMechanism`, `sharedResources` | 并发场景维度 |

每个 Entity 还携带 `sourceExcerpt` 字段，保留原文中与该模块直接相关的段落。

### 3.5 System 查询机制

5 个 System 通过 Component 组合查询筛选目标实体：

| System | 查询条件 | 审查焦点 |
|:-------|:---------|:---------|
| StateConcurrency | `state.involved && concurrency.involved` | 竞态、脏数据、死锁 |
| AiState | `ai.involved && state.involved` | AI 非确定性输出污染持久化层 |
| AiConcurrency | `ai.involved && concurrency.involved` | 高并发下 AI 服务雪崩 |
| ChaosInjection | 所有实体 | 故障注入 + 降级兜底检测 |
| AntiCorruptionAudit | `ai.involved` | 防腐层完整性审计 |

## 4. 三阶段管线实现细节

### Phase 1：增强型实体提取

- **实现文件**：`src/systems/entity-extractor.ts`
- **双重提取**：文档超过 `dualExtractionThreshold`（默认 8000 字符）时，按 `##` 标题边界分为前后两段，并行提取后按 `entity.id` 合并去重
- **分段策略**：`splitDocument()` 在中点 ±500 字符范围内寻找最近的 `## ` 标题作为切割点
- **重试保护**：每次 AI 调用均包裹 `withRetry`，最多重试 2 次，指数退避

### Phase 2：并行交叉审查

- **实现文件**：`src/systems/` 下 5 个独立 System 文件
- **执行方式**：`Promise.all` 并行拉起 5 个 System，零数据依赖
- **后处理**：
  1. 合并 4 个 System 的漏洞列表
  2. `deduplicateVulnerabilities()` 基于标题关键词去重
  3. 代码层 `.filter(v => v.level === "P0").slice(0, config.p0Limit)` 硬过滤

### Phase 3：混合渲染管线

| 章节 | 渲染方式 | 实现 |
|:-----|:---------|:-----|
| §1 方案评估 | **结构化输出**（路线 A） | `generateObject` + `SectionsASchema` |
| §2 潜在风险 | **模板硬渲染** | `renderVulnerabilitiesSection()` |
| §3 优化建议 | **结构化输出**（路线 A） | 同 §1，合并为一次调用 |
| §4 深度解析 | **Few-Shot 增强**（路线 B） | `generateText` + Few-Shot 消息注入 + Pro 模型 |
| §5 混沌测试 | **模板硬渲染** | `renderChaosSection()` |

- 路线 A 和路线 B 通过 `Promise.all` 并行
- `assembleDocument()` 从结构化数据直接拼接，**零正则依赖**

## 6. 横切关注点实现

### 6.1 配置中心化（`src/config.ts`）

```typescript
export const config = {
  inputPath, outputPath, fewShotPath,   // I/O 路径（支持环境变量覆盖）
  p0Limit: 5,                           // P0 漏洞上限
  chaosDisplayLimit: 3,                 // 混沌测试展示上限
  contextMaxTokens: 3000,              // Phase 2 上下文 Token 预算
  renderContextMaxTokens: 4000,        // Phase 3 渲染上下文 Token 预算
  models: {
    extraction: "gemini-3-flash-preview",
    analysis: "gemini-3-flash-preview",
    rendering: "gemini-3-flash-preview",
    deepAnalysis: "gemini-2.5-pro",     // 深度解析用更强模型
  },
  retry: { maxAttempts: 2, backoffMs: 1000 },
  dualExtractionThreshold: 8000,
};
```

### 6.2 重试机制（`src/utils/retry.ts`）

- 通用 `withRetry<T>` 泛型函数，支持指数退避
- 所有 9 次 AI 调用均包裹重试逻辑
- 失败时打印带 label 的告警日志

### 6.3 智能截断（`src/utils/truncate.ts`）

- `smartTruncate()`：保留首 60% + 尾 30%，中间插入省略标记
- `splitDocument()`：在中点附近的 `##` 标题边界切割，供双重提取使用

### 6.4 Token 追踪（`src/utils/token-tracker.ts`）

- `TokenTracker` 类，兼容 AI SDK v6 的 `inputTokens`/`outputTokens` 字段名
- 每次 AI 调用后调用 `tracker.record(phase, usage)` 记录
- 管线结束时调用 `tracker.printSummary()` 输出分阶段用量表格

## 7. 当前方案优点

### 7.1 架构层面

| 优点 | 说明 |
|:-----|:-----|
| **ECS 解耦** | 实体提取与漏洞分析彻底解耦，每个 System 只关注特定 Component 组合 |
| **并行化** | Phase 2 的 5 个 System + Phase 3 的 2 路渲染均 `Promise.all` 并行 |
| **双重提取容错** | 长文档分段提取 + 合并去重，消除 Phase 1 单点故障 |
| **结构化渲染** | 路线 A 改用 `generateObject`，彻底消除正则解析脆弱性 |

### 7.2 质量控制

| 优点 | 说明 |
|:-----|:-----|
| **Zod Schema 强约束** | 所有 AI 输出通过 Zod Schema 校验，类型安全 |
| **漏洞去重** | 基于标题关键词去重，避免多 System 输出冗余漏洞 |
| **P0 硬过滤** | 代码层 `.filter().slice()` 硬性控制，不依赖 AI 自律 |
| **模板+AI 混合** | §2/§5 模板硬渲染格式 100% 可控，AI 仅负责创造性章节 |

### 7.3 工程化

| 优点 | 说明 |
|:-----|:-----|
| **模块化拆分** | 从单文件 550 行拆为 17 个模块文件，职责单一 |
| **配置外化** | 所有阈值/路径/模型名统一在 `config.ts` 管理，支持环境变量覆盖 |
| **全链路重试** | 9 次 AI 调用均有指数退避重试 |
| **Token 成本可观测** | 每次运行结束输出分阶段 Token 用量 |
| **模型分级** | 深度解析用 Pro 模型，其余用 Flash，兼顾质量与成本 |

## 8. 当前方案不足与改进方向

### 8.1 仍存在的 P0 级问题

| 编号 | 问题 | 影响 | 改进方案 |
|:-----|:-----|:-----|:---------|
| **P0-A** | **实体完整性无校验** | 双重提取虽然降低了漏提风险，但没有机制验证提取结果是否覆盖了文档的所有 `##` 级标题。如果两段都漏提了同一个模块，仍然无感知 | 增加"实体覆盖率校验"：提取文档的 `##` 标题列表，与 Entity.id 做模糊匹配，对未覆盖的标题发出告警或触发补充提取 |
| **P0-B** | **`generateObject` 已被 AI SDK v6 标记 `@deprecated`** | 当前使用 `// @ts-ignore` 绕过。未来 SDK 版本可能移除此 API，导致代码不可用 | 迁移至 `generateText` + `output: object({ schema })` 的新写法，需等 `Output.object` 在运行时正确导出后立即迁移 |
| **P0-C** | **路线 B 仍使用正则提取 Few-Shot 样本** | `ai-renderer.ts` 中 `fewShotExample.match(/### 4\. 深度解析[\s\S]*$/)` 从样本文件中提取内容，样本格式变化会导致匹配失败 | 将 Few-Shot 样本改为结构化 JSON 格式，或用独立的 `few-shot-section4.md` 文件直接加载 |

### 8.2 P1 级：质量与可靠性

| 编号 | 问题 | 影响 | 改进方案 |
|:-----|:-----|:-----|:---------|
| **P1-A** | **去重算法过于粗糙** | 当前仅取标题前 30 个字符做关键词匹配，两个语义相同但措辞不同的漏洞（如"Session 竞态"和"会话并发冲突"）无法去重 | 引入 AI 语义去重 System，或使用 Embedding 向量相似度（余弦距离 < 0.15 判定为重复） |
| **P1-B** | **智能截断的 Token 估算不精确** | 中文 1.5 字符/token 仅为粗略估计，实际因代码片段/标点混合而偏差较大 | 接入 `tiktoken` 或直接使用 AI SDK 的 `countTokens` API 做精确计算 |
| **P1-C** | **无断点续跑** | 9 次 AI 调用即使 Phase 2 最后一个 System 失败，也要从 Phase 1 重跑 | 引入 Phase 级别的中间结果持久化（如写入 `.cache/phase1.json`），断点续跑时直接加载缓存 |
| **P1-D** | **Token 追踪无预算控制** | 当前仅监控不告警，无法在 Token 超限前主动终止 | 在 `TokenTracker` 中增加 `budget` 字段和 `checkBudget()` 方法，超限时抛出 `BudgetExceededError` |

### 8.3 P2 级：工程化

| 编号 | 问题 | 影响 | 改进方案 |
|:-----|:-----|:-----|:---------|
| **P2-A** | **无单元测试** | `dedup.ts`、`truncate.ts`、`template-renderer.ts`、`assembler.ts` 均为纯函数，但没有测试覆盖 | 使用 Vitest 编写测试，优先覆盖纯函数模块 |
| **P2-B** | **`TokenTracker.record` 使用 `any` 类型** | 为兼容 AI SDK v5/v6 的字段名差异，使用了 `usage?: any`，丢失类型安全 | 定义 `CompatibleUsage` 联合类型，或用 `LanguageModelUsage` 做精确类型约束 |
| **P2-C** | **System Prompt 硬编码在代码中** | 每个 System 的大段中文 Prompt 嵌入在 `.ts` 文件中，修改 Prompt 需要改代码 | 将 Prompt 外化到 `prompts/` 目录下的 `.md` 文件，运行时动态加载 |
| **P2-D** | **无输出质量评估** | 无法自动判断一次审查的质量是否达标 | 增加简单的输出质量检查：漏洞条数 ≥ 2、每个章节字数 ≥ 100 字、Entity 数量 ≥ 3 等 |

## 10. 总结

TDD-Reviewer v4 完成了从"单文件原型"到"模块化生产工具"的关键进化：

**已落地的核心改进**：
1. ✅ Phase 1 双重提取 + 合并去重 — 消除单点故障
2. ✅ 路线 A 改用 `generateObject` — 消除 `assembleDocument` 的正则脆弱性
3. ✅ 全链路指数退避重试 — 9 次 AI 调用均有容错
4. ✅ 漏洞去重 — 避免多 System 输出冗余
5. ✅ 智能截断 — 保留首尾内容，不再粗暴 slice
6. ✅ 模型分级 — 深度解析用 Pro，其余用 Flash
7. ✅ Token 成本可观测 — 分阶段用量汇总
8. ✅ 工程化拆分 — 17 个模块文件，Barrel Export

**下一步优先级**：
1. 🔴 迁移 `generateObject` → `generateText` + `output` 新 API（追踪 SDK 发布）
2. 🔴 实体覆盖率校验（补全双重提取的最后一环）
3. 🟡 AI 语义去重替代关键词去重
4. 🟡 Phase 级中间结果缓存 + 断点续跑
5. 🟢 Vitest 单元测试覆盖纯函数
6. 🟢 Prompt 外化到独立文件
